{% load i18n ui accounts_tags %} {% comment %} The operational steps taken during the incident (A.5.26 / ISO 27035) : isolate the host, revoke the token, pull the logs before they rotate. Rendered inline by `IncidentDetailView` on first paint and swapped into `#response-actions` by `incidents:response-actions` after an add or an edit, so it must stand on its own. Context : `incident`, `response_actions` (deadline order, as the view and the model ordering give them) and `response_action_form`, which is absent for a reader without `incidents.incident.update`. Unlike its two append-only neighbours in this module, this row is **mutable by design** : moving from planned to done while the incident is live is its whole purpose. It carries a plain `status` column and no lifecycle, so there is no stepper here and none is owed - the row's governance is the incident's governance, and the edit and delete controls point at the two routes the URLconf actually offers. An action past its deadline and still expected to be worked tints `table-danger` on the row itself : mid-incident, that must never be something an operator has to click to find. {% endcomment %} {% has_perm "incidents.incident.update" as can_update_incident %} {% if response_action_form and can_update_incident %} {% comment %} The add form, inline : the view already built it, and a round trip to render an empty form is a round trip spent in the window where delay is the harm. It posts to the same create route as the card header's button, and targets the drawer so a rejected action comes back with its field errors instead of replacing the table with a form. {% endcomment %}
