{% load i18n ui accounts_tags %} {% comment %} The incident chronology : the single narrative an auditor, a supervisory authority or a court reads. Rendered inline by `IncidentDetailView` on first paint and swapped into `#timeline-entries` by `incidents:timeline-entries` after an append, so it must stand on its own : it opens no tag it does not close and assumes no wrapper. Context : `incident`, `timeline_entries` (oldest first, as the view, the model ordering and the register export all order them) and `timeline_entry_form`, which is absent for a reader without `incidents.incident.update`. **Append-only, and the markup says so.** No edit control, no delete control, no status select : the model refuses every write against an existing row and the URLconf offers neither route. A factual error is corrected by appending an entry that supersedes the earlier one with a stated reason, and both stay visible, linked to each other in both directions. The list is walked `reversed` rather than re-ordered in the view : the stored order is the narrative order the export writes, and re-sorting it here would give the same incident two different chronologies on two surfaces. The card shows the latest act first because that is what a responder mid-incident reads. A `lifecycle` row - one the platform appended from a transition, that nobody typed - is tinted, carries the accent rule and states its source, so a line the organisation wrote is never mistaken for a line the platform wrote. {% endcomment %} {% has_perm "incidents.incident.update" as can_update_incident %} {% if timeline_entry_form and can_update_incident %} {% comment %} The append form, inline : reaching for the drawer costs a round trip in the window where delay is the harm, so the form the view already built is offered where the chronology is read. It posts to the same create route as the header button, and targets the drawer so a rejected entry comes back with its field errors rather than replacing the card with a form. {% endcomment %}
